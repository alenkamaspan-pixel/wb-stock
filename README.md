# WB Stock — учёт остатков по FBS-складам

Внутреннее приложение для учёта остатков товара на ваших складах при продаже
по схеме FBS на Wildberries. Показывает, сколько и где лежит товара,
автоматически списывает остаток при поступлении заказов от WB и отправляет
актуальные цифры обратно в WB, чтобы карточка не улетала в «нет в наличии»
или не продавала то, чего физически нет.

## Как это устроено

Текущий остаток нигде не хранится отдельным числом — он всегда считается
как сумма всех движений товара (приход, продажа по заказу WB, перемещение
между складами, списание). Это защищает от рассинхрона: если что-то пошло
не так, остаток всегда можно пересчитать заново по истории и видно, откуда
взялась любая цифра.

Раз в `SYNC_INTERVAL_MINUTES` минут (по умолчанию 20) приложение:
1. забирает из WB новые заказы (сборочные задания) и сразу списывает товар
   с того склада, с которого WB просит собрать заказ;
2. проверяет статусы ранее полученных заказов — если заказ отменён,
   возвращает товар на остаток;
3. отправляет в WB актуальные остатки по всем затронутым товарам и складам.

Кнопка «Синхронизировать сейчас» на дашборде запускает то же самое вручную.

Приход товара от поставщика и перемещения между складами вносятся руками —
WB не знает о них ничего, это исключительно ваши внутренние данные.

## Стек и почему он такой

Flask + встроенный в Python sqlite3 + чистый HTML/Jinja2, без тяжёлых
зависимостей (SQLAlchemy, FastAPI и т.п.) — специально, чтобы это можно было
поднять максимально быстро и без сюрпризов при установке пакетов. Для
вашего текущего масштаба (WB, один магазин, несколько человек) этого с
запасом достаточно. Если объём вырастет — см. раздел «Известные ограничения
и что доделать при росте» ниже.

## Запуск локально

```bash
cd wb-stock-app
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
# откройте .env и впишите как минимум SECRET_KEY и ADMIN_PASSWORD
python3 -m app.main
```

Откройте http://localhost:8000 — при первом запуске автоматически создаётся
администратор с логином/паролем из `ADMIN_USERNAME`/`ADMIN_PASSWORD` (по
умолчанию `admin` / `admin`, обязательно смените в `.env`).

## Как получить токен WB API

Личный кабинет продавца → Настройки → Доступ к API → создать токен со
скоупами **Marketplace** и **Statistics** (можно один токен сразу с двумя
скоупами). Впишите его в `.env` в `WB_MARKETPLACE_TOKEN` (и
`WB_STATISTICS_TOKEN`, если выпускали отдельно).

**Важно перед боевым запуском:** WB периодически меняет форматы методов
API. Прежде чем подключать реальный токен, сверьте пути и формат тела
запроса в `app/wb_client.py` с актуальным Swagger
(https://dev.wildberries.ru/en/swagger/orders-fbs и
https://openapi.wildberries.ru/marketplace/api/en/) — все обращения к сети
нарочно собраны в одном файле, чтобы такую сверку было легко сделать за
10–15 минут.

## Первая настройка после запуска

1. Зайдите под администратором.
2. Склады → «Импортировать список складов из WB» — подтянет ваши склады,
   зарегистрированные в WB, вместе с их WB ID. Сверьте названия.
   Если нужен склад, который не синхронизируется с WB (например,
   «брак» или «в пути») — добавьте его вручную с выключенным флагом
   «Синхронизировать с WB».
3. Товары → добавьте товары со штрихкодом (обязательно — по нему WB matчит
   остатки) и, если знаете, артикулом WB (nmId).
4. Движения → внесите текущий фактический остаток как «Приход» по каждому
   товару и складу — это стартовая точка учёта.
5. Пользователи → добавьте нужных людей с ролями:
   - **admin** — полный доступ, включая управление пользователями;
   - **manager** — может вносить приход/перемещения/списания;
   - **viewer** — только просмотр.

## Деплой на Railway (самый быстрый вариант)

1. Зарегистрируйтесь на railway.app, «New Project» → «Deploy from GitHub
   repo» (или «Empty Project» и залейте файлы через Railway CLI, если кода
   ещё нет в GitHub — тогда сначала создайте пустой репозиторий и запушьте
   туда содержимое этой папки).
2. В настройках проекта добавьте Variables (переменные окружения) — все
   значения из `.env`, которые вы заполнили локально: `SECRET_KEY`,
   `ADMIN_USERNAME`, `ADMIN_PASSWORD`, `WB_MARKETPLACE_TOKEN`,
   `WB_STATISTICS_TOKEN`, `SYNC_INTERVAL_MINUTES`.
3. **Подключите Volume** (постоянный диск) — Settings → Volumes → Add
   Volume, примонтируйте, например, в `/data`. Установите переменную
   `DATABASE_PATH=/data/wb_stock.db`. Без этого шага база будет обнуляться
   при каждом передеплое!
4. Railway сам подхватит `Procfile` и запустит `gunicorn`. После первого
   деплоя откройте выданный домен — увидите страницу входа.

## Деплой на Render (альтернатива)

Аналогично: New → Web Service → подключить репозиторий → Build Command
`pip install -r requirements.txt`, Start Command — как в `Procfile`. На
бесплатном тарифе Render диск не сохраняется между деплоями — для
постоянного хранения базы нужен платный план с Persistent Disk, либо сразу
переходить на Postgres (см. ограничения ниже).

## Переменные окружения

Смотрите `.env.example` — там подробные комментарии по каждой. Коротко:

| Переменная | Назначение |
|---|---|
| `DATABASE_PATH` | путь к файлу SQLite |
| `WB_MARKETPLACE_TOKEN` / `WB_STATISTICS_TOKEN` | токены WB API |
| `SYNC_INTERVAL_MINUTES` | как часто синхронизироваться с WB |
| `SECRET_KEY` | ключ для подписи сессий — сгенерируйте случайную строку |
| `ADMIN_USERNAME` / `ADMIN_PASSWORD` | учётка первого администратора |

## Известные ограничения и что доделать при росте

Это сознательно упрощённый MVP под текущий масштаб (один магазин на WB) —
сделан так, чтобы запуститься максимально быстро. Дальше по мере роста
понадобится:

- **Ozon.** Пока не подключён. Добавляется как второй клиент по образцу
  `wb_client.py` плюс отдельная логика в `sync.py` — данные Ozon устроены
  немного иначе (кластеры вместо отдельных складов), но общая схема
  (журнал движений + пуш остатков) переиспользуется.
- **Несколько магазинов/аккаунтов (мультитенантность).** Сейчас все
  пользователи видят одни и те же данные одного магазина. Для нескольких
  независимых магазинов с изоляцией данных нужна отдельная сущность
  «магазин» и её id в каждой таблице — это сознательно отложенная задача
  (обсуждали отдельно).
- **SQLite → Postgres.** При росте до многих тысяч SKU или нескольких
  одновременных пользователей стоит перейти на Postgres — весь доступ к
  БД сосредоточен в `app/database.py`, менять нужно будет только его.
- **Сверка со Statistics API.** Основной источник списания — заказы
  Marketplace API (быстрее и точнее по времени). Данные `/supplier/sales`
  для контрольной сверки за сутки в код пока не добавлены — стоит
  подключить как отдельный ночной отчёт о расхождениях, а не как
  автоматическую корректировку остатка.
- **CSRF-защита форм** не реализована — приемлемо для внутреннего
  инструмента за логином, но стоит добавить, если планируете открывать
  доступ шире.
- **`gunicorn -w 1`** (один воркер) в `Procfile` — это осознанно: фоновая
  синхронизация запускается как поток внутри процесса, при нескольких
  воркерах она задублируется. Если понадобится больше пропускной
  способности — синхронизацию нужно вынести в отдельный процесс/воркер
  (например, отдельный сервис на Railway с cron), а веб-часть тогда можно
  scale-ить независимо.
- **Статусы заказов WB.** Список статусов, которые считаются отменой
  (`CANCEL_STATUSES` в `app/sync.py`), собран по документации и может быть
  неполным — после первых реальных заказов стоит свериться с тем, что
  реально приходит от WB, и дополнить список.
